# F4.1 — Standardisert kunde-onboarding (read-only audit)

> Mål: en ekstern kunde skal gå fra repository-tilgang til forståelig audit-rapport og
> konkret tilbud **uten at Tom manuelt bygger rapporten**. Hele flyten er scriptet.

## Flyten (6 steg)

| # | Steg | Eier | Verktøy |
|---|---|---|---|
| 1 | Kontakt + eksplisitt samtykke | Tom | `packages/audit/customers/<id>.json` (consent-gate) |
| 2 | Minimum tilgang (read-only) | Kunde | leseklon / read-only deploy key |
| 3 | Scope-definisjon | Tom + kunde | `scope.description` + `scope.exclude` i manifesten |
| 4 | Kjøring av audit | Hermes/CLI | `npm run audit -- <repo> --customer <id>` |
| 5 | Leveranser (3 filer, isolert) | Automatisk | kunderapport + teknisk appendix + evidence |
| 6 | Build Proposal-gjennomgang | Tom-gate | utkastet i kunderapporten → godkjenning FØR Build |

## 1. Eksplisitt consent/scope (hard gate)

- Opprett `packages/audit/customers/<id>.json` fra `_template.json`.
- **Audit nektes** (exit 2) uten: `consent_granted: true`, definert `scope.description`, `access.level: "read_only"`.
- Manifesten inneholder **aldri** hemmeligheter — `assertNoSecrets()` avbryter hvis den matcher secret-mønster.

## 2. Minimum nødvendige tilgangsnivåer

| Nivå | Hva | Trengs for audit? |
|---|---|---|
| Repo-les (read:contents) | leseklon / read-only deploy key / GitHub App | ✅ **eneste som trengs** |
| Repo-skriv (push) | deploy key med skriv | ❌ aldri |
| Prod-/staging-tilgang | konsoll, SSH, kube | ❌ aldri |
| Secret-tilgang | env-filer, hemmelighets-kuberter, API-nøkler | ❌ aldri — **aldri kopiert inn i Arch** |
| Tredjeparts-API-tokens | Stripe/Slack/Sentry m.fl. | ❌ aldri |

**Regel:** Arch trenger kun *lesetilgang til kodebasen*. Alt annet avslås — det er også et salgsargument («vi trenger bare å se koden»).

## 3. Data-isolasjon per kunde

- Manifest: `packages/audit/customers/<id>.json` (metadata kun — ingen secrets, ingen kontaktinformasjon i audit-output).
- Output: `docs/audits/customers/<id>/` (3 filer: `.md`, `.technical.md`, `.evidence.json`).
- Secret-scan skriver **aldri verdier** — kun `fil:linje` + mønster-navn (i kunderapport og evidence).
- Kunde-data blandes aldri med interne audits (`docs/audits/`).

## 4. Design partner-modus (første eksterne pilot)

`"mode": "design_partner"` i manifesten → rapporten merkes «Design partner (pilot)».
Se `docs/f4.1-design-partner.md`.

## 5. Regler som ALDRI brytes under audit

1. **Read-only:** ingen endringer i kundens kode, ingen deploy, ingen ny infrastruktur.
2. **Ingen secrets inn i Arch:** verken manifest, rapport eller evidence.
3. **Ingen implementasjon i audit-fasen:** kundens kode røres først i Arch Build, etter godkjenning.
4. **Juridisk/regulatorisk = aldri påstand:** GDPR m.fl. rapporteres som «ikke vurdert — krever kvalifisert gjennomgang».
