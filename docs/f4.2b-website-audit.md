# F4.2B — Arch Website Audit v1

> **Status:** Ferdig (F4.2B). Default low-friction entry inn i Arch Audit.
> **Commit:** se git-log (F4.2B). **Release-frost:** repo-audit engine frosset ved `c9b724a` — dette er en *ny* web-modul, ikke en endring av repo-audit.

## Hva det er

En **utenfor-inn, read-only** audit av en offentlig nettside — kun ut fra URL. Kunden gir oss:

```
@url:https://kunde.no
```

og får en evidensbasert vurdering av nettsiden **uten repo-tilgang, uten å endre noe**.

Dette er **laveste terskel** inn i Arch-salgs­trakten:

```
Website Audit  →  Build Proposal  →  Teknisk/Repository-audit (nivå 2, ved behov)  →  Arch Build  →  Arch Managed
```

Repo-auditen (Audit v1, F4.1) er **ikke erstattet eller svekket** — den er nivå 2, for kunder som allerede har sett verdi og vil gi intern tilgang.

## Kjøring

```bash
# Uformell prospekt-vurdering (ingen manifest, ingen samtykke — intern bruk)
npm run audit:web -- @url:https://kunde.no

# Formell kunde-audit (krever customers/<id>.json med consent_granted + scope)
npm run audit:web -- @url:https://kunde.no --customer <id>

# Design-partner (som kunde, men merket pilot)
npm run audit:web -- @url:https://kunde.no --customer <id> --design-partner
```

Output (3 filer, isolert per kunde):
- `<website-audit-<domene>.md>` — executive (daglig leder)
- `<website-audit-<domene>.technical.md` — teknisk appendix (utvikler/byrå)
- `<website-audit-<domene>.evidence.json` — maskinlesbar evidence (alt sporbart)

## Hva som sjekkes (8 dimensjoner)

| Dimensjon | Vekt | Hva |
|---|---|---|
| Performance | 20 | komprimering, cache, render-blokkering, bildeoptimalisering, tredjepart |
| Security Surface | 20 | HTTPS/TLS, sikkerhetsheadere, versjons-avsløring, sensitive filer (kun offentlig observerbar) |
| UX / Mobile | 15 | viewport, responsiv-CSS-signal, mobil-skjermbilde |
| Accessibility | 15 | lang-attributt, alt-tekst, skjemaetiketter, overskriftshierarki |
| SEO / Discovery | 10 | meta title/description, canonical, og:, sitemap/robots |
| Reliability | 10 | HTTP-status, omdirigeringskjede, ødelagte lenker, ressurs-feil |
| Trust / Privacy | 5 | trackere/analytics (signal, ikke FAIL), CMP, cookie |
| Automation Potential | 5 | CTA/lead-muligheter, manuelle arbeidsflyter som kan automatiseres |

**UNKNOWN ≠ PASS:** «frahold av bevis» skal aldri bli et negativt faktum. Ukjente sjekker merkes `UNKNOWN` og teller som ikke-verifisert — ikke som stryk.

## Sikkerhetsgrenser (harde)

- **Read-only, alltid.** Kun passive HTTP GET/HEAD. Ingen mutasjoner, ingen skjema-submit, ingen login-bypass, ingen exploits, ingen brute-force.
- **Ingen aggressive tester.** Port-scan, SQLi/XSS-prober osv. = forbudt. Kun normal HTTP-trafikk.
- **Ingen secrets inn i Arch.** Scanneren skriver kun `fil:linje + mønsternavn`, aldri verdier.
- **Ingen fabrikasjon.** Core Web Vitals kun hvis faktisk målbar (browser); ellers `observed/estimated/unknown`. Ingen GDPR/WCAG-sertifiseringspåstander — kun «signal»/«potential concern»/«requires legal review».
- **Provenance på alt.** Hver sjekk har `evidence` + `confidence` (high/medium/low).
- **Crawl-sikkerhet.** `max_pages` (25), `max_depth` (3), `delay_ms` (300), robots.txt-respekt, same-origin-only, rate-limit.

## Scoring

Egen website-scoreprofil — gjenbruker **ikke** repository Health Score (de måler forskjellige ting). Vekter dokumentert over. Total = vektet snitt av kjente dimensjoner; `UNKNOWN` dimensjoner telles som ikke-verifisert (teller ikke mot score, men rapporteres).

## Funn → 4 bøtter (samme kommersielle lag som repo-audit)

🔴 **Critical** · 🟠 **High ROI** · 🟢 **Quick Win** · 🔵 **Strategic** — hver med problem / forretningsmessig betydning / anbefalt løsning / forventet innsats / build-kandidat.

Build-kandidater (`build_candidate: true`) mates automatisk inn i **Arch Build Proposal-utkast**.

## Arkitektur

```
packages/audit/
  audit-web.mjs          CLI-orchestrator (@url:, --customer, --prospect-preview)
  lib/web/
    kinds.mjs            WEB_KINDS (website-funn-typer) → merges inn i commercial KIND_META
    collect.mjs          fetch-innsamling (A–J) m/ provenance + crawl-sikkerhet
    score.mjs            website Health Score (8 dimensjoner)
    findings.mjs         FAIL-sjekker + browser-evidence + automatiserings-signaler → funn
    browser.mjs          headless Chrome best-effort (dump-dom + skjermbilder)
    report.mjs           executive + teknisk + evidence
  lib/commercial.mjs     (patchet: WEB_KINDS import) — 4 bøtter + 5 felt + Automation Potential
  lib/customer.mjs       (patchet: website-manifest, prospect_preview, web-output-dir)
```

Gjenbruker consent/scope-gate, kunde-isolasjon, bøtter og Build Proposal fra repo-audit — ikke en one-off.

## Åpne risikoer

- **Render-blokkering-sjekken** er heuristisk (medium confidence) — kan over-/under-rapportere for komplekse SPA-er (type=module håndtert, men inline-skript og nomodule-fallback er gråsone). V2.4-kandidat.
- **Browser-målinger** (LCP/CLS/console-feil) er best-effort — Chrome dump-dom gir bare delvis; rik DevTools-protokoll-måling er backlog (ARC-7/v2.4).
- **example.com 44%** demonstrerer at en tom placeholder scorer lavt (ingen SEO/innhold/lead) — ønsket oppførsel, men «kontakt-skjema»-funnet treffer også legitime sider uten lead-behov (f.eks. dokumentasjonssider).
