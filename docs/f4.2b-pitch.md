# F4.2B — Website Audit pitch (salgs­trakten, førstesteg)

> Tom sin ordlyd (innbakt i alle kundevendte rapporter):
> **«Vi analyserer programvaren deres uten å endre noe, finner risiko, teknisk gjeld og automatiseringsmuligheter, og gir dere en prioritert plan for hva som faktisk er verdt å gjøre.»**
> — IKKE si «AI-plattform» først. Trapp: **Audit → Build → Managed.**

## Én-linjer for førstekontakt

> «Gi oss URL-en deres, så gir vi dere en gratis, utenfor-inn analyse av nettsiden — risiko, teknisk gjeld og hva som faktisk er verdt å automatisere. Uten å endre noe, uten tilgang til koden.»

Kunden trenger **kun** å gi:

```
@url:https://kunde.no
```

Ingen login, ingen repo-tilgang, ingen installasjon, ingen endring. Laveste mulige terskel.

## Hvorfor dette virker som førstesteg

1. **Null risiko for kunden** — read-only, ingen mutasjoner, ingen exploits. Vi *leser* bare det som allerede er offentlig.
2. **Umiddelbar verdi** — en prioritert plan leveres i løpet av minutter, ikke uker.
3. **Bevis før tillit** — kunden ser kvaliteten FØR de gir intern tilgang (repo-audit = nivå 2).
4. **Naturlig oppsalg** — hvert funn med `build_candidate` blir et Build Proposal-utkast.

## Trappen

```
Website Audit (gratis, URL)        ← F4.2B (denne)
  ↓
Build Proposal (auto-utkast)
  ↓
Teknisk/Repository-audit (nivå 2, kunden gir intern tilgang)
  ↓
Arch Build (separat fase, egen tilgang)
  ↓
Arch Managed (løpende drift/forvaltning)
```

## Hva kunden får (3 filer)

- **Executive-rapport** — for daglig leder: score, toppfunn i 4 bøtter, prioritert liste, Build Proposal.
- **Teknisk appendix** — for utvikler/byrå: per-sjekk evidence + confidence.
- **Evidence JSON** — maskinlesbar, alt sporbart (provenance).

## Grenser vi holder

- Aldri påstå «sikker»/«compliant»/«healthy» uten evidence. Kun «signal»/«potential concern»/«requires legal review».
- Aldri mutere, aldri skjema-submit, aldri login-bypass.
- Aldri fabrikkere tall (Core Web Vitals kun hvis målbar).
- Aldri utvide scope uten eksplisitt samtykke.

## Skille mot repo-audit

| | Website Audit (F4.2B) | Repository Audit (F4.1) |
|---|---|---|
| Input | URL alene | Repo-tilgang + samtykke |
| Terskel | Lavest | Høyere (kunde gir intern tilgang) |
| Scope | Offentlig observerbar nettside | Kildekode, CI/CD, secrets, deps |
| Rolle i trakt | Førstesteg | Nivå 2 |
