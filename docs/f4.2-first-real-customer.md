# F4.2 — First Real Customer (kommersielt bevis)

> **Release-frosset:** Arch Audit v1 er frosset ved commit `c9b724a`. Ingen nye generelle
> engine-features uten evidence fra et ekte kunde-case.

## Målet

Ta den **første faktiske eksterne organisasjonen** gjennom hele flyten:

```
Lead → Consent → Read-only Audit → Executive Report → Review
     → Build Proposal → Commercial Decision → Arch Learning
```

## GATE: PROVEN WITH REAL CUSTOMER

**Kan kun passere** etter faktisk kundeleveranse OG tilbakemelding.
Bilglass-piloten og offentlige repos er test/reference evidence — **ikke erstatning** for denne gaten.

## Det som allerede er klart (F4.1, gjenbrukes uendret)

- Kunde-registrering: `packages/audit/customers/<id>.json` (consent/scope/read-only-gate)
- Isolert audit: `docs/audits/customers/<id>/`
- Executive Report + Technical Appendix + Build Proposal (auto)
- Design partner-modus

## Det F4.2 legger til: måling + feedback + læring

### 1. Leveranse-registrering (`_delivery.template.json` + `record-delivery.mjs`)

Hver kundeleveranse får en record i `customers/<id>.delivery.json`:

```bash
npm run audit:delivery -- <id>           # auto-beregn maskin-måltall + skriv record
npm run audit:delivery -- <id> --check   # valider PROVEN-gate
```

| Felt | Auto | Menneske | Beskrivelse |
|---|---|---|---|
| `timing.audit_machine_ms` | ✅ | — | Maskin-tid for selve audit-kjøringen |
| `timing.lead_to_consent_hours` | — | ✅ | Timer fra lead til signert samtykke |
| `timing.total_elapsed_hours` | — | ✅ | Total leveranse-tid (lead → rapport levert) |
| `timing.manual_steps` | — | ✅ | Antall manuelle steg Tom måtte gjøre |
| `timing.automation_rate_pct` | — | ✅ | Andel automatisert (1 − manuelle/total) |
| `findings.by_category` | ✅ | — | Funn per kategori (fra evidence) |
| `findings.build_candidates` | ✅ | — | Antall Build-kandidater |
| `findings.customer_cared_about` | — | ✅ | Hvilke funn kunden faktisk brydde seg om |
| `customer.objections` / `questions` | — | ✅ | Innvendinger / spørsmål fra kunden |
| `customer.feedback` | — | ✅ | Kvalitativ tilbakemelding |
| `commercial.outcome` | — | ✅ | no_go / build_agreed / build_declined / follow_up |
| `learning.knowledge_graph_entries` | — | ✅ | Knowledge Graph-filer opprettet fra læringen |

### 2. Kundefeedback → Knowledge Graph

Etter kundemøtet: funn som overrasket, som var uklare, eller som kunden avviste,
variggjøres i `packages/knowledge-engine/knowledge/{failures,lessons}/` — som for
Bilglass (`audit-v1-root-only-scanning.md`) og fastapi (`audit-v1-node-centric.md`).

## Pitchen (ordrett — IKKE «AI-plattform» først)

> «Vi analyserer programvaren deres uten å endre noe, finner risiko, teknisk gjeld og
> automatiseringsmuligheter, og gir dere en prioritert plan for hva som faktisk er verdt å gjøre.»

- **Arch er motoren**, ikke første setning. Kunden kjøper et konkret resultat.
- Når kunden ser resultatet, selger Arch Build (og senere Arch Managed) seg selv.

## Regler som ALDRI brytes (også i F4.2)

1. Ikke endre kundekode under Audit.
2. Ikke kopier secrets.
3. Ikke utvid scope uten eksplisitt samtykke.
4. Ikke merk kunden «healthy», «secure» eller «compliant» uten evidence.
